# Investigation: Moo States for Expression Parsing in Markdown Content

## Question
Can `moo.states()` handle stepping into the expression parser automatically in relevant markdown content, while ignoring headers, quotes, lists, etc.? Can it also step into inline solve?

## Discoveries

- **Current Lexer State Machine Usage**: `MarkdownLexer.ts` defines `main`, `expression`, `heading`, `blockquote`, `list_item`, `inline`, and `inline_solve` states.
    - **`main` state**: Entry point that detects markdown constructs and expression rules. It is currently used by `MarkdownEditorViewPlugin` to check if a line is a markdown construct.
    - **`expression` state**: Pure expression rules, currently unused (defined but not entered).
    - **`heading`, `blockquote`, `list_item` states**: Tokenize content after markers. They now include `INLINE_SOLVE_START` to handle inline solves within markdown content.
    - **`inline_solve` state**: Tokenizes expression content inside `s`...``.
- **Dual-Line Processing**: `MarkdownEditorViewPlugin` uses CodeMirror's syntax tree to mask markdown constructs (headings, lists, etc.) and then processes *only non-masked lines*. This is the "two-tier" approach that the "single moo lexer" plan aims to replace.
- **Inline Solve Extraction**: The `Preprocessor` and `InlineSolveExtractor` use regex `/s\`([^`]*)\`/g`. This logic is currently duplicated in `MarkdownEditorViewPlugin.findInlineSolves`.
- **Engine Isolation Check**: `src/engine/` imports `@/constants/locales` (which imports `UserSettings`). This is an Obsidian-specific import that needs to be moved or abstracted for engine portability.

## Implementation Notes

- **Lexer Integration**: When updating `MarkdownLexer`, ensure the `main` state is used for full-document parsing (not line-by-line). The `expression` state can be kept for inline expressions or removed.
- **Preprocessor Removal**: The `Preprocessor` directory can be deleted entirely after moving its logic (markdown masking, comment removal, inline solve extraction) into the moo lexer states.
- **CodeMirror Masking Removal**: The `MarkdownEditorViewPlugin` logic that uses `syntaxTree` to compute `doNotSolveMask` must be removed. The new lexer will handle markdown constructs natively.
- **Portability**: The engine's dependency on `@/constants/locales` (which uses `UserSettings`) must be broken. Move locale data into `src/engine/constants/locales/` or make the engine accept a locale interface.
- **Testing**: After lexer changes, ensure that the existing provider tests (arithmetic, percentage, etc.) still pass, as they rely on the `Lexer` API.

## Potential Solutions

### Solution 1: Enhanced State Transitions
Keep the current state structure but enhance it to handle inline expressions within markdown content:
- When in `heading`/`blockquote`/`list_item` states, allow inline solve syntax
- Transition to `inline_solve` state when `s` is detected
- Pop back to the markdown state when the inline solve ends

### Solution 2: Hybrid Approach
Use moo states for markdown detection and a separate expression parser for content:
- Moo states detect markdown constructs and extract content
- Content is then passed to an expression parser
- This might be more efficient than trying to handle everything in moo

### Solution 3: Full Integration
Integrate expression parsing fully into moo states:
- All states include expression rules
- Inline solve transitions work across all states
- More complex but potentially more elegant
