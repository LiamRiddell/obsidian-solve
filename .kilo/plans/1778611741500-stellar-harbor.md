## Phase 2: Single Moo State-Machine Lexer (#3, #10, #12, #13)

**Replace the two-tier architecture with a single moo-based markdown lexer using states.** Moo's native `push`/`pop` state transitions are the right mechanism — they avoid redundant line-iteration, eliminate the lezer dependency, and make the engine portable as an npm package.

### Design

A single `MarkdownLexer` class with moo states for document-level and expression-level tokenization:

```
main state (document-level triggers → push):
  ├─ `^#{1,6}\s` → push heading_state → consume → pop
  ├─ `` ^```[^`]*$ `` → push fenced_code_state → consume until closing `` ``` `` → pop
  ├─ `^\$\$$` → push math_block_state → consume until `\$\$` → pop
  ├─ `^>\s?` → push blockquote_state → match rest-of-line content as expression → pop
  ├─ `^[-*+]\s` → push list_state → match rest-of-line as expression → pop
  ├─ `^\[\[` → skip wikilink content → pop
  ├─ `^%%` → skip comment → pop
  ├─ `s\`` → push inline_state → match content → pop on `` ` `` (already exists)
  ├─ `#` or `//` → push comment_state → consume rest of line → pop
  ├─ `$` or `$$` → push mathjax_state → pop on closing delimiter
  └─ [no match] → push expression_state → tokenize normally

expression state (current Lexer.ts):
  └─ numbers, operators, keywords, identifiers, etc.
     └─ `s\`` → push inline_state → pop on `` ` ``

inline state (already exists):
  └─ content between backticks

heading / fenced_code / math_block states:
  └─ generic "skip until done" rules
```

### Key architectural decisions

**Why single moo lexer beats two-tier:**
1. **Single pass** — moo reads the input once, state transitions are O(1) stack operations
2. **No CodeMirror dependency** — the lexer takes a plain string, works in any JS runtime. For npm packaging, `createDocumentLexer()` starts in `main` state; `createExpressionLexer()` starts directly in `expression` state — both use the same rule definitions.
3. **No lezer** — the syntax tree walk + mask construction disappears entirely
4. **No Preprocessor** — comments, mathjax, markdown constructs are moo states, not regex pre-processing
5. **Line numbers built-in** — moo tracks `line` and `col` on every token natively. The `MarkdownEditorViewPlugin` can still reconcile via `view.state.doc.lineAt(pos)` from the token's offset.

**How multi-line constructs work:**
- Fenced code: `main` matches `` ``` `` opening, pushes `fenced_code` state. That state has a single rule `{ match: /[^]*?(?=```|$)/, lineBreaks: true }` that consumes everything until the closing fence or EOF, then pops.
- Math blocks: same pattern with `$$` delimiters
- Blockquotes: each `>` line is classified individually (no multi-line state needed — the expression state handles the content after `>`)
- Callouts: `> [!note]` is just a blockquote — the content after `> [!note]` is an expression

**How markdown-skipped lines reconcile with inline solves:**
- `# Heading with s\`1+2\` `: the `main` state matches `^#` and pushes `heading` state. But within heading, `s\`` can match and push `inline`. After the inline pop, heading resumes.
- `> note s\`1+2\` `: `main` matches `^>`, pushes `blockquote`. Expression tokens and `s\`` work normally within blockquote state.
- This is a **net gain** over the current lezer approach which skips ALL content in masked regions.

**Handling incomplete/partial input (per TODO #10):**
- Moo automatically produces `undefined` at end of input — the parser handles this gracefully
- Each state has a fallback `ERROR` rule so moo never crashes on unrecognized input
- Unclosed fences/math blocks: the greedy `[^]*?(?=delimiter|$)` matches until EOF

### Resilience guarantee: no single bad line crashes the engine

This is a hard requirement. The lexer lives in an Obsidian plugin that processes every visible line on every keystroke. One line of garbage must not break solving on 500 other lines.

**Three-layer defense:**

1. **Lexer layer:** Every moo state has an `ERROR: moo.error` fallback. Moo's contract is: on unrecognized input, produce an ERROR token and advance one character. It NEVER throws. Every state also has `lineBreaks: true` on consumptive rules so long runs don't accumulate position errors.

2. **Parser layer:** `Parser.parseExpression()` catches errors from missing parselets. If a token has no registered prefix parselet, the parser returns a sentinel `Value.error()` instead of throwing. The `ExpressionEngine.evaluateLine()` wraps parsing in try/catch and returns `undefined` for that line — other lines unaffected.

3. **Editor layer:** `MarkdownEditorViewPlugin.buildDecorations()` catches per-line evaluation errors in `buildLineDecorations()`. If one line fails, `decorations` is empty for that line but the `builder.add()` loop continues for all other lines. The `RangeSetBuilder` is never corrupted.

**Per-line isolation is the key design principle:** Every line evaluation is independent. The `LineCache` stores per-line entries. The `MemoCache` keys on line text + line number. A crash in line N only poisons line N's cache entry, not the entire cache. The `DependencyGraph` tracks per-line variable dependencies — variable errors propagate, but syntax errors don't.

**What is explicitly tested:**
- A 100-line document where lines 5, 27, 53, 88 are garbage (random binary, unicode, HTML) — lines 1-100 all evaluated safely, only garbage lines produce `undefined` / no decoration
- A single 10MB line of `"a"` characters — lexer produces one IDENT token per word boundary or ERROR token per char, doesn't OOM (moo processes streamingly)
- Line containing only U+0000 (null) — ERROR token, next line processed normally

**Fuzz testing: every input type the lexer will ever see:**
The lexer tests in Phase 2 already cover extensive fuzz cases (category 6). The purpose of this Phase 10 section is to make those fuzz tests executable at the test-runner level — a dedicated test file or generator that runs them every build.

**Mechanics:**
- A test file `test/engine/lexer/LexerFuzz.spec.ts` (separate from the main lexer tests for clarity)
- Uses `test.each()` with a large fixture array of ~200+ inputs covering all 6 categories from Phase 2
- Every test assertion is simply: "this does not throw" + "the returned tokens array has length >= 0" + "no token type is `undefined`"
- No fragile value assertions on most fuzz cases — just structural guarantees

- Hand-written edge cases (~100 cases)

- Runs in a single `describe` block with `jest.setTimeout(30000)` for the large inputs

**End-to-end pipeline fuzz:**
- `engine.evaluateLine(lineNumber, arbitraryString)` never throws for any string — returns `undefined` at worst
- `MarkdownEditorViewPlugin.buildDecorations(view)` never throws for any document content — produces a valid `DecorationSet` at worst
