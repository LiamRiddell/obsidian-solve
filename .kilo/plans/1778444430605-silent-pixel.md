# Parsing Engine Rewrite Plan

## Architecture Overview

```
Full visible document text (visibleRanges from CodeMirror) — RAW text
         │
         ▼
┌──────────────────────────────────────────────────┐
│  Lexer (moo) — ONE PASS                          │  ← moo.reset(fullText) once
│  Handles ALL text natively in its single /y RegExp│  Token types include: NUMBER, PLUS, COMMENT,
│  Markdown elements, comments, mathjax are just   │  MATHJAX, BLOCKQUOTE, HEADING, LIST_ITEM, etc.
│  token types — no preprocessor stripping needed   │  Inline solve uses push/pop state transitions
└──────────────────────┬───────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────┐
│  Token Grouper + Filter                          │  group by .line → Map<line, Token[]>
│  1. Group raw tokens by .line                    │

### What moo handles natively (no Preprocessor needed)

moos single compiled RegExp per state handles ALL text in one pass. The following are just token types:

| Input | Token Types Produced | Result |
|-------|--------------------|--------|
| `1 + 2` | NUMBER, PLUS, NUMBER | Parsed normally |
| `# this is a comment` | COMMENT (entire line) | Line skipped entirely |
| `1 + 2 // inline comment` | NUMBER, PLUS, NUMBER, COMMENT | COMMENT filtered, rest parsed |
| `> 1 + 2` | BLOCKQUOTE, NUMBER, PLUS, NUMBER | BLOCKQUOTE filtered, rest parsed |
| `- list item` | LIST_ITEM (entire line) | Line skipped entirely |
| `## Heading` | HEADING (entire line) | Line skipped entirely |
| `$$x^2$$` | MATHJAX (entire line) | Line skipped entirely |
| `s\`1 + 2\`` | IDENT(s), BACKTICK_OPEN, ... push to inline state, CONTENT, BACKTICK_CLOSE pop back | Inline solve extracted |
| `200 USD in GBP` | NUMBER, UNIT, KEYWORD(in), UNIT | Verb pattern matched |

The Preprocessor is **eliminated** — moo handles everything with its single RegExp. The "filter" step is just checking each token's type and skipping known-ignore types. This is O(n) in tokens and involves zero string copying/transformation.

### Worker Thread execution — preventing UI freezing

The engine is designed to run on a **Web Worker** (or Node.js Worker Thread for desktop Obsidian) to prevent UI freezing during large document updates:

```ts
// Main thread:
const solveWorker = new Worker('solve-engine.worker.js');

// On document change, send visible ranges to worker
solveWorker.postMessage({
  type: 'SOLVE',
  text: visibleText,
  variables: currentVariableCache,
});

// Worker responds with results
solveWorker.onmessage = (e) => {
  const { lineResults, highlights } = e.data;
  applyDecorations(lineResults, highlights);
};
```

**Worker-friendly design of the engine:**

| Component | Worker-safe? | Notes |
|-----------|-------------|-------|
| moo lexer | Yes | Pure function: input string → token array. No DOM, no Obsidian API calls |
| BytecodeBuilder | Yes | Pure data transformation. No side effects |
| VM executor | Yes | Stack machine. Pure computation. No async needed |
| LineClassifier | Yes | Token array → bytecode. Pure logic |
| **Community plugins** | **Conditionally** | Plugins that do network calls (stock ticker, Runescape lookup) need careful design |

**Plugin isolation in worker context:**
```ts
// Plugin registers its parselet + opcode handler
// The opcode handler CANNOT do direct DOM/API calls inside the VM
// Instead: the handler writes a "side effect request" to a buffer
// After VM execution, the main thread reads the buffer and executes side effects

// Inside worker:
solve.registerOpcode(OpCode.PLUGIN_RS_LOOKUP, (vm, opcodes, ip, numbers, strings) => {
  const itemName = strings[opcodes[ip++]];
  // Instead of fetching directly, signal back to main thread:
  pendingSideEffects.push({ type: 'RS_LOOKUP', name: itemName, resultSlot: slotIndex });
  return ip;
});

// After all lines executed, worker sends pendingSideEffects to main thread
// Main thread fetches prices, sends results back
// Worker re-executes only the affected lines with resolved values
```

**Benefits:**
- **Zero UI freezing** — all lexing, parsing, compiling, and VM execution happens off the main thread
- **Community plugins still work** — network calls are handled on main thread via side-effect buffer pattern
- **Single-pass efficiency** — worker receives full visible text, processes in one batch, returns all results
- **Obsidian 1.0+ supports Workers** — `new Worker()` works in Electron/desktop

**Trade-off considerations:**
- Serialization overhead (token arrays, bytecode, results) — minimal for text + numbers
- Plugin registration needs to happen in both worker (parselets, opcodes) and main thread (side effects)
- Can fall back to main-thread execution if Worker is unavailable (mobile Obsidian)

### How patterns work — three tiers of flexibility

The engine uses a **Line Classifier** that tries multiple parsing strategies in order. Each strategy is a self-contained parser that emits bytecode. This matches Ohm's flexibility but without the grammar DSL overhead.

**Tier 1 — Standard Pratt expressions** (`10 plus 10`, `sqrt(4)`, `1 + 2 * pi`):
```
Tokens: [NUMBER(10), KEYWORD(plus), NUMBER(10)]
  → Pratt parser with parselet registry
  → BinaryOpParselet for PLUS (keyword mapped to PLUS token type via moo.keywords())
  → emit: [PUSH 10, PUSH 10, ADD]
```
"plus" is matched by moo's KEYWORD rule via `moo.keywords()` wrapper. The wrapper checks if the matched identifier text (lowercased) is in the keyword map: `{plus: 'PLUS', minus: 'MINUS', ...}`. It returns `'PLUS'` as the token type, so the Pratt parser's PLUS infix parselet handles it — exactly the same as `+`.

**Tier 2 — Verb patterns** (`convert 200 USD to GBP`, `200 USD in GBP`):
```ts
// Built-in or plugin-registered verb pattern
solve.registerVerbPattern({
  // Trigger: line starts with "convert" or ends with "in X"
  matchTokens: (tokens) => {
    if (tokens.length < 4) return null;
    // "convert" "200" "USD" "to" "GBP"
    if (tokens[0]?.type === 'KEYWORD' && tokens[0]?.value === 'convert') {
      return {
        pattern: 'convert',
        value: tokens[1],         // NUMBER(200)
        fromUnit: tokens[2],       // UNIT(USD)
        toUnit: tokens[4]          // UNIT(GBP)
      };
    }
    // "200" "USD" "in" "GBP"
    if (tokens[2]?.type === 'KEYWORD' && tokens[2]?.value === 'in') {
      return {
        pattern: 'in',
        value: tokens[0],
        fromUnit: tokens[1],
        toUnit: tokens[3]
      };
    }
    return null;
  },
  compile: (match, builder) => {
    // Emit bytecode: push value, push from unit, push to unit, convert
    builder.emitOpcode(OpCode.PUSH_NUMBER);
    builder.emitNumber(parseFloat(match.value.value));
    builder.emitOpcode(OpCode.PUSH_STRING);
    builder.emitString(match.fromUnit.value);
    builder.emitOpcode(OpCode.PUSH_STRING);
    builder.emitString(match.toUnit.value);
    builder.emitOpcode(OpCode.UOM_CONVERT);
  }
});
```

**Tier 3 — Prefix/custom patterns** (`::rs ge Rune Axe`, `$AAPL`):
```ts
// Plugin registers a line prefix pattern  
solve.registerPrefixPattern({
  prefix: '::rs',  // lines starting with ::rs
  parse: (tokens, builder) => {
    // tokens: [PREFIX(::rs), IDENT(ge), IDENT(Rune), IDENT(Axe)]
    // ge = "Grand Exchange" price lookup
    const itemName = tokens.slice(1).map(t => t.value).join(' ');
    builder.emitOpcode(OpCode.PLUGIN_CUSTOM);
    builder.emitString('rs-lookup');
    builder.emitString(itemName);
  }
});

// The ::rs prefix is a moo token: PREFIX matches /::[a-z]+/
// The Line Classifier detects lines starting with registered prefixes
// BEFORE trying the standard Pratt parser
```

### Reactive Dependency Tracking — high-frequency variable updates

The engine must handle time-varying expressions like `:myVariable = random_ticker(0, 20, 2s)` where a variable changes every 2 seconds, triggering re-evaluation of all downstream consumers (e.g. `Damage = s`:myVariable + 20``) without naive global re-evaluation.

#### 1. Dependency Tracking via DAG

A **Directed Acyclic Graph** maps every variable definition to its consumers:

```ts
class DependencyGraph {
  // Variable → Set of downstream consumer line numbers
  private consumers: Map<string, Set<number>> = new Map();
  
  // Line number → Set of variables it reads
  private dependencies: Map<number, Set<string>> = new Map();

  // Phase 1 — BUILD: After full-document lex+parse, walk all lines
  // For each line, record which variables are READ vs WRITTEN
  registerLine(lineNumber: number, reads: string[], writes: string[]): void {
    for (const dep of reads) {
      if (!this.consumers.has(dep)) this.consumers.set(dep, new Set());
      this.consumers.get(dep)!.add(lineNumber);
    }
    if (writes.length > 0) {
      this.dependencies.set(lineNumber, new Set(reads));
      for (const write of writes) {
        // A write SHADOWS previous definitions — see §3
        const prevConsumer = this.consumers.get(write);
        if (prevConsumer) prevConsumer.delete(lineNumber); // remove self
      }
    }
  }

  // Phase 2 — PROPAGATE: When a variable changes, collect all transitively affected lines
  getAffectedLines(changedVariable: string): Set<number> {
    const visited = new Set<number>();
    const queue = [changedVariable];
    while (queue.length > 0) {
      const varName = queue.pop()!;
      const consumers = this.consumers.get(varName);
      if (!consumers) continue;
      for (const line of consumers) {
        if (visited.has(line)) continue;
        visited.add(line);
        // If this consumer also WRITES a variable, its consumers must be notified too
        const deps = this.dependencies.get(line);
        if (deps) {
          for (const dep of deps) {
            if (!visited.has(dep)) queue.push(dep);
          }
        }
      }
    }
    return visited;
  }
}
```

#### 2. Granularity: Expression-level reactive updates

Rather than re-evaluating entire lines, the system re-evaluates only the **expression containing the changed variable**. Each line may contain multiple expressions (e.g., inline solves `s`...``, `:var + 1`, etc.). The expression-level granularity works via:

```ts
class ExpressionResult {
  lineNumber: number;
  expression: string;        // "Damage = :myVariable + 20"
  bytecode: BytecodeProgram;  // compiled bytecode — cached
  lastResult: Value;          // last computed value — memoized
  readVariables: string[];    // [:myVariable] — discovered during compilation
  writeVariable: string|null; // Damage — if this is an assignment
}
```

When `:myVariable` updates:
1. DAG finds consumer lines (e.g., line 210 with `Damage = ...`)
2. Only line 210's expression is re-executed (bytecode VM run)
3. Other expressions on line 210 are unchanged
4. If `Damage` is used elsewhere, those lines are enqueued too

#### 3. Shadowing and Scope

Variables are **lexically scoped by line number** — a definition on line 200 affects lines 201+, but not lines < 200:

```ts
class ScopeManager {
  // For each variable, ordered list of (lineNumber, value) pairs
  private definitions: Map<string, {line: number, expr: ExpressionResult}[]> = new Map();

  write(variable: string, lineNumber: number, expr: ExpressionResult): void {
    if (!this.definitions.has(variable)) {
      this.definitions.set(variable, []);
    }
    const stack = this.definitions.get(variable)!;
    // Push new definition — active for all subsequent lines
    stack.push({ line: lineNumber, expr });
    // Remove old definitions that are shadowed
    stack.sort((a, b) => a.line - b.line);
  }

  read(variable: string, readLine: number): Value | undefined {
    const stack = this.definitions.get(variable);
    if (!stack) return undefined;
    // Find the definition with the highest line number ≤ readLine
    for (let i = stack.length - 1; i >= 0; i--) {
      if (stack[i].line <= readLine) return stack[i].expr.lastResult;
    }
    return undefined;
  }

  invalidateDownstream(variable: string, definitionLine: number): void {
    // When a variable is redefined, all downstream variables that were
    // defined using the OLD value must be re-evaluated
    const stack = this.definitions.get(variable);
    if (!stack) return;
    // Find the index of the current definition
    const idx = stack.findIndex(s => s.line === definitionLine);
    if (idx === -1) return;
    // Remove all subsequent definitions of this variable (they were shadowed)
    stack.splice(idx + 1);
  }
}
```

The DAG naturally handles shadowing: when line N defines `:x`, all prior definitions of `:x` are shadowed for lines > N. The `consumers` map only tracks the ACTIVE definition per scope region.

#### 4. Optimization Strategies

**Push-based reactivity** (event-driven):
```
random_ticker callback fires → new value for :myVariable
  → DependencyGraph.getAffectedLines(":myVariable") → {line 210}
  → LineCache.markDirty(210)
  → VM re-executes only line 210's bytecode
  → new result for "Damage"
  → if "Damage" has consumers, recurse
```

**Memoization**:
```ts
class MemoCache {
  // expression hash → last result + epoch
  private cache: Map<number, { result: Value, epoch: number }> = new Map();
  private epoch = 0;
  
  getOrCompute(expr: string, line: number, compute: () => Value): Value {
    const hash = fastHash(expr + line);
    const existing = this.cache.get(hash);
    if (existing && existing.epoch === this.epoch) return existing.result;
    const result = compute();
    this.cache.set(hash, { result, epoch: this.epoch });
    return result;
  }
  
  invalidate(variable: string): void {
    this.epoch++;  // Bump epoch to invalidate ALL downstream caches
  }
}
```

**Dirty flags via LineCache** (already in plan):
```
LineCache:
  Map<lineNumber, { result: Value, bytecode: Bytecode, dependencies: string[], dirty: boolean }>
  
  When variable changes → DAG → affected lines → mark dirty
  Re-render only dirty lines → clear dirty flag
```

**Batched updates for high-frequency sources**:
```
random_ticker with 2s interval:
  → values are pushed to a queue
  → every 100ms (or requestAnimationFrame), process the batch:
    1. Collect all pending variable updates
    2. Union the affected line sets via DAG
    3. Re-execute all affected lines in a single batch
    4. Update CodeMirror decorations in one shot
  → Prevents 20 individual re-renders per second
```

#### 5. Complexity Analysis

| Operation | Time | Space | Notes |
|-----------|------|-------|-------|
| DAG build (initial) | O(E + V) where E = variable references, V = variables | O(E + V) | Single pass after lex+parse. Each expression's `readVariables` + `writeVariable` is recorded |
| DAG update (re-parse) | O(E_dirty) | O(1) incremental | Only the changed line's edges are updated |
| Affected lines query | O(V + C) where C = consumer count | O(V) recursion stack | BFS/DFS over the graph. Worst case = full graph on root variable change |
| Single variable update | O(C_log) — log consumers of one variable | O(1) | Direct Map lookup. Most variables have 1-5 consumers |
| Shadow resolution | O(S log S) — sort shadow stack per variable | O(S) per variable | S rarely exceeds 2-3 (re-definitions are uncommon) |
| Memo cache hit | O(1) | O(N) where N = unique expressions | Hash lookup per expression per line |
| Batch update (100ms) | O(K * avg_deps) where K = changed variables | O(merged_lines) | Merged dirty set prevents duplicate re-execution |

**Real-world estimate**: A document with 500 expressions and 20 variables, with `:myVariable` changing every 2 seconds:
- DAG size: ~520 edges (500 reads + 20 writes)
- Single variable update: ~5-15 lines re-executed (not 500)
- Batch overhead: ~0.1ms per affected expression (VM execution)
- Total per 2s tick: ~0.5-1.5ms of CPU — imperceptible to the user

The old Ohm approach required writing a grammar rule for everything. The new approach uses **token-level pattern matching** — it's strictly more flexible because:

1. **Parselets handle operator expressions** (arithmetic, vector ops, etc.) — same flexibility as Ohm grammar rules but in plain TS
2. **Verb patterns handle natural language** (convert X to Y, X in Y) — these were hard to express in Ohm's PEG syntax
3. **Prefix patterns handle custom plugin syntax** (::rs, $AAPL) — impossible in Ohm without modifying core grammars
4. **All emit bytecode into the same builder** — VM execution is unified regardless of pattern origin

Compared to Ohm-JS, the key advantages:
- **No grammar compilation step** — patterns are just TS functions
- **Patterns compose naturally** — you can use the Pratt parser INSIDE a verb pattern for the value part
- **Debugging is just TS debugging** — no Ohm trace needed
- **Performance** — pattern matching is simple token array scans, not PEG backtracking

## Phased Migration Plan

### Phase 0: Foundation (test infrastructure + new empty engine)

**Goal**: Set up the new engine directory with the building blocks, no functionality yet. Run tests to prove zero-regression on old code.

**Steps**:
1. Create `src/engine/` directory structure (lexer/, vm/, parser/patterns/, parser/registry/, providers/)
2. Install `moo` dependency (`npm install moo`)
3. Write `Value.ts` — discriminated union `{type: 'number'|'hex'|'string'|..., value: number|bigint|string|...}`. No class hierarchy, no `accept()`/`visit()`.
4. Write `OpCode.ts` — enum of all bytecode opcodes (PUSH_NUMBER, PUSH_HEX, ADD, SUB, MUL, DIV, MOD, EXP, NEG, LSHIFT, RSHIFT, CALL, LOAD_VAR, STORE_VAR, etc.)
5. Write `BindingPower.ts` enum (precedence levels)
6. Write `Parselet.ts` base types (`PrefixParselet`, `InfixParselet`) — parselets emit opcodes into BytecodeBuilder, they do NOT create AST nodes
7. Write `Token.ts` type definitions and `TokenRegistry.ts` skeleton
8. Write `Lexer.ts` — moo wrapper, full-document single-pass lexer with state machine.
   - **One lexer pass per document**: Feed the full visible text to `moo.states()`. moo tracks `.line` and `.col` natively on every token (requires `lineBreaks: true` on NEWLINE rule). After tokenization, group tokens by `.line` — each line's tokens are parsed independently.
   - **No regex flags**: moo compiles all rules into a single RegExp per state and does NOT support `/i`, `/g`, or `/u` regex flags. Use `[a-zA-Z]` ranges for character classes instead of `\w` with flags.
   - **Case-insensitive keywords via `moo.keywords()`**: Define an `IDENT` token with `{match: /[A-Za-z_][A-Za-z0-9_]*/, type: ciKeywords({...})}` where `ciKeywords` is a wrapper around `moo.keywords()` that lowercases the matched text before lookup. This gives automatic keyword/identifier disambiguation (solves the `className` → `class` + `Name` bug) and case-insensitivity without massive character classes.
   - **States with `push`/`pop` for inline solve**: When the `main` state encounters `s\``, `push: 'inline'` transitions to the inline state. Backtick in inline state `pop: 1` returns to main. The inline state only matches CONTENT (anything except backtick) and the closing BACKTICK.
   - **Unicode safety via `moo.error`**: `ERROR: moo.error` catches EVERY unmatched character including non-ASCII, CJK, emoji, RTL text. Instead of throwing, returns an ERROR token. This prevents silent data corruption in multilingual documents.
   - **`save()` / `reset(state)` for incremental re-lex**: After initial full-document tokenization, dirty-line re-processing saves the lexer state at the start of the dirty line range, resets, and only tokenizes the affected lines. This avoids re-lexing the entire document on small edits.
9. Write `BytecodeBuilder.ts` — flat opcode buffer builder with methods `emitOpcode(op)`, `emitNumber(n)`, `emitString(s)`, `emitIndex(i)`. Produces `{opcodes: Uint8Array, numbers: Float64Array, strings: string[]}`.
10. Write `VM.ts` — stack-based bytecode interpreter. Pre-allocated `Float64Array(64)` value stack. Single `execute(bytecode)` function with `switch(opcode)` dispatch loop. Returns `Value`.
11. Write `OpRegistry.ts` — plugins register custom opcode handlers. Each handler receives `(vm, bytecode, ip) => ip` (modify stack, return next instruction pointer).
12. Write `Parser.ts` — Pratt parser that feeds into BytecodeBuilder. Parselets call `builder.emitOpcode()`, NOT `return new SomeNode()`.
13. Write `Preprocessor.ts` — full-document preprocessor. Strips comments, markdown lists, mathjax. Finds expression boundaries. Returns cleaned text spans with line mapping preserved.
14. Write `ParseletRegistry.ts` with registration API
15. Write pattern type interfaces in `src/engine/parser/patterns/`:

### Phase 6: Dynamic data + Reactive dependency tracking

**Goal**: High-frequency variable updates (stock tickers, `random_ticker(0,20,2s)`, crypto prices) with DAG-based targeted re-evaluation. Only downstream consumers of a changed variable are re-executed, not the entire document.

**Steps**:
1. Build `DependencyGraph` class:
   - `consumers: Map<string, Set<number>>` — variable name → line numbers that READ it
   - `dependencies: Map<number, Set<string>>` — line number → variables it READS
   - `registerLine(line: number, reads: string[], writes: string[])` — record edges
   - `getAffectedLines(changedVar: string): Set<number>` — BFS for transitive consumers
2. Build `ScopeManager` class for lexical scoping by line number:
   - `write(var: string, line: number)` → push definition to stack, shadow prior definitions for subsequent lines
   - `read(var: string, readLine: number)` → find active definition (highest line ≤ readLine)
   - `invalidateDownstream(var: string, definitionLine: number)` → when a variable is redefined, clear all downstream shadowed definitions
3. Build `MemoCache` class:
   - `getOrCompute(expr: string, line: number, compute: () => Value): Value`
   - `invalidateAll()` / `invalidate(variable: string): void` — epoch-based bulk invalidation
4. Build `ExpressionResult` record per line:
   - `lineNumber`, `expression`, `bytecode: BytecodeProgram`, `lastResult: Value`, `readVariables: string[]`, `writeVariable: string|null`
   - Compiled bytecode is **cached** and only re-compiled when the expression text changes
5. Extend `LineCache` with dependency metadata:
   ```ts
   class LineCacheEntry {
     result: Value;
     bytecode: BytecodeProgram;
     readVariables: string[];
     writeVariable: string | null;
     dirty: boolean;
   }
   ```
6. `IDynamicDataSource` interface (from original Phase 6):
   ```ts
   interface IDynamicDataSource {
     name: string;
     refreshIntervalMs: number;
     fetch(symbol: string): Promise<number | string>;
   }
   ```
7. `DynamicValueResolver` — background polling loop:
   - Each poll: `source.fetch(symbol)` → update cache → if value changed → call `DependencyGraph.getAffectedLines(symbol)` → mark all affected lines dirty → schedule batch re-render
   - Batch re-render: at most once per 100ms (or rAF), collect all dirty lines from the queue, re-execute their bytecode, update decorations
   - Pause polling when Obsidian window is unfocused
8. Token + parselet integration for `random_ticker(0, 20, 2s)`:
   - Lexer token: `RANDOM_TICKER` keyword
   - Parselet: parses args `(from, to, interval)` → emits opcode `DICE_ROLL_TIMED` with interval parameter
   - VM executor: on `DICE_ROLL_TIMED`, doesn't roll immediately — instead registers a timer callback and pushes the current value
   - On each timer tick: new random value → push to variable → trigger DAG propagation
9. Example implementations:
   - `random_ticker(from, to, interval)` — built-in
   - Stock ticker plugin: `$AAPL` → dynamic data source with 60s poll → DAG propagates to consumers
   - `:myVariable = random_ticker(0, 20, 2s)` + `Damage = s`:myVariable + 20``
10. Write tests:
    - DAG build + query: 3 variables, 10 lines, verify transitive propagation
    - Shadowing: variable redefined on line 50, line 60 reads it correctly, line 40 reads OLD value
    - MemoCache: verify epoch bump invalidates downstream
    - Dynamic ticker: mock ticker fires 5 times, verify only 1 batch render (debounced)
11. **Verify**: Run `npm test` — old tests pass, new DAG/reactive tests pass

## Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Parser algorithm | Pratt (top-down operator precedence) | Simple, extensible, excellent for expression languages. Each parselet is tiny and self-contained |
| Intermediate representation | **Bytecode** (flat opcode array, not AST) | Zero GC allocations during parse/execute. ~3-5 CPU instructions per op. Value stack pre-allocated. No visitor pattern, no instanceof dispatch |
| Execution model | **Stack-based VM** switch(opcode) loop | Single function dispatch. Plugins register opcode handlers. Cache-friendly sequential execution |
| Lexer | moo — full-document single pass | One `lexer.reset()` call per update cycle. moo tracks `.line`/`.col`/`.offset` natively. Groups tokens by line for per-line parsing |
| Lexer doc processing | Full text → tokens grouped by `.line` | Single regex engine pass for entire visible range. No per-line reset overhead |
| Markdown/comments/mathjax | Handled natively by moo as token types | Comment, Heading, Blockquote, ListItem, MathJax are just token types. TokenFilter strips them. No preprocessor, no string copying/transformation |
| Worker thread | Engine runs in Web Worker | Pure data transformations (tokenize, compile, execute) are all synchronous and Obsidian-API-free. Plugin side effects use a pending-queue pattern: worker queues requests, main thread resolves them
| Case-insensitive keywords | `moo.keywords()` wrapper with auto-lowercase | `moo.keywords()` handles longest-match disambiguation. Wrapper lowercases match text for case-insensitive keyword detection |
| Inline solve | moo states with `push: 'inline'` / `pop: 1` | s\` triggers state push → inline tokenizer runs → closing backtick pops back to main state |
| Unicode / no silent errors | `ERROR: moo.error` catches ALL unmatched input | Any character (including non-ASCII, emoji, CJK) that doesn't match a rule produces an ERROR token instead of being silently dropped. This prevents data corruption in multilingual documents |
| Number/BigInt | Size-aware + syntax dispatch | `0x...`, `...n` suffix, or overflow detection → BigInt; else Number |
| Result representation | `Value` discriminated union — `{type, value}` plain object or `[type, value]` tuple | Single type. No class hierarchy. No `accept()`/`visit()`. Formatter uses `switch(value.type)` |
| Community plugins | Register: tokens, parselets, opcode handlers, functions, units, variable sources | Separate npm packages. Core engine knows nothing about plugin domains. Runescape item lookup, stock tickers, custom units are all external plugins |
| Variable resolution | Fetch + re-parse | Variable values inserted into expression string, re-tokenized and re-parsed. Cached per variable |
| Caching | LFU (existing) + LineCache (new) | Two-level: expression-level (LFU) + line-level (dirty tracking) |
| Dynamic data | Polling engine via OpRegistry + dirty-line invalidation | Stock tickers, crypto prices update at configurable rates, trigger re-execution of affected lines |
| Syntax highlighting | CodeMirror 6 DecorationSet via token-type mapping | Each moo token maps to a CSS class. Only tokens from valid parse lines get highlighted |

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Behavior divergence from Ohm grammars | Phase 1 parallel comparison with exhaustive test corpus |
| moo doesn't handle all token patterns | moo supports full RegExp with sticky flag; fall back to manual tokenizer for edge cases |
| Variable cross-document parsing is slow | VaultSource caches; re-parse only on file change (via Obsidian events) |
| Plugin API breaking changes for existing community providers | Keep old event-based registration working during migration, deprecate in Phase 10 |
| Performance regression during migration | Benchmark gates at each phase; abort and optimize before proceeding |
