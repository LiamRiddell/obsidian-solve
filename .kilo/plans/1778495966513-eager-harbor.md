# Phase 7: CodeMirror 6 Syntax Highlighting Integration

## Goal

Syntax highlighting for recognized expressions in the editor. Only successfully parsed lines get styled — unparsed text is unaffected. Uses the new engine's Lexer + Parser to determine which tokens are valid expression tokens.

## Current State

- **`ExpressionEngine`** (`src/engine/engine/ExpressionEngine.ts`): Full Lexer + Parser + VM pipeline, creates `LineCache` entries per line
- **`Lexer`** (`src/engine/lexer/Lexer.ts`): moo-based lexer producing tokens with `.type`, `.value`, `.offset`, `.line`, `.col`
- **`LineCache`** (`src/engine/cache/LineCache.ts`): Per-line result cache with dirty tracking
- **`MarkdownEditorViewPlugin`** (`src/codemirror/MarkdownEditorViewPlugin.ts`): Existing view plugin using OLD pipeline system; builds result decorations
- **`Token.ts`** (`src/engine/lexer/Token.ts`): Token type definitions including all expression token types
- **No highlight CSS classes** exist yet

### Step 3: Add `getTokenRanges()` helper to `Lexer`


This is a convenience method that:
1. Calls `reset(lineText)`

3. Filters out WS and NEWLINE tokens

### Step 4: Create `SolveHighlightProvider`

**File (NEW)**: `src/codemirror/SolveHighlightProvider.ts`

A class that builds highlight `DecorationSet` from the Lexer's token output.

```ts
import { RangeSetBuilder } from "@codemirror/state";
import { Decoration, DecorationSet, EditorView } from "@codemirror/view";
import { Lexer } from "@/engine/lexer/Lexer";
import { Parser } from "@/engine/parser/Parser";
import { ParseletRegistry } from "@/engine/parser/registry/ParseletRegistry";
import { LineCache } from "@/engine/cache/LineCache";

export class SolveHighlightProvider {
  private lexer: Lexer;
  private parser: Parser;

  constructor(registry: ParseletRegistry) {
    this.lexer = new Lexer();
    this.parser = new Parser(registry);
  }

  buildHighlightDecorations(
    view: EditorView,
    visibleRanges: readonly {from: number, to: number}[],
    lineCache: LineCache,
    validExpressionLines: Set<number>
  ): DecorationSet {
    const builder = new RangeSetBuilder<Decoration>();

    for (const { from, to } of visibleRanges) {
      const range = view.state.doc.iterRange(from, to);
      let nextLineOffset = 0;

      for (const lineTextRaw of range) {
        const linePos = from + nextLineOffset;
        const line = view.state.doc.lineAt(linePos);

        // Only highlight lines that were successfully parsed
        if (!validExpressionLines.has(line.number)) {
          nextLineOffset += lineTextRaw.length;
          continue;
        }

        // Try to get cached highlights first
        const cachedEntry = lineCache.get(line.number);
        if (cachedEntry?.highlights && cachedEntry.highlights.length > 0) {
          for (const h of cachedEntry.highlights) {
            builder.add(
              h.from,
              h.to,
              Decoration.mark({ class: h.className })
            );
          }
          nextLineOffset += lineTextRaw.length;
          continue;
        }

        // No cache, tokenize and attempt parse
        const tokens = this.lexer.getHighlightTokens(line.text);
        if (tokens.length === 0) {
          nextLineOffset += lineTextRaw.length;
          continue;
        }

        // Attempt parse — only highlight if full parse succeeds
        const filteredTokens = tokens.filter(t => t.type !== "WS" && t.type !== "NEWLINE");
        // ... use lexer token positions to build decorations
        // Map token offset (in lineText) to document position: line.from + token.offset

        nextLineOffset += lineTextRaw.length;
      }
    }

    return builder.finish();
  }
}
```

Key details:
- The `Lexer` token `.offset` is relative to the input string (`line.text`)
- Map to document position: `line.from + token.offset`
- Token `.value.length` gives the span length in the document
- If parse fails, do NOT emit any decorations for that line — highlight only complete valid expressions
- Emit `Decoration.mark({class: className})` for each token that has a mapped CSS class
- Cache highlight ranges in `LineCacheEntry.highlights` for subsequent renders

### Step 5: Modify `MarkdownEditorViewPlugin` to emit highlight decorations

**File**: `src/codemirror/MarkdownEditorViewPlugin.ts`

Changes:
1. Import `SolveHighlightProvider` and `ExpressionEngine`
2. Store an `ExpressionEngine` instance (or share the one from the broader integration)  
3. In `buildDecorations()`, after building result decorations, also call `SolveHighlightProvider.buildHighlightDecorations()` and merge the two decoration sets
4. Track which lines were successfully parsed (valid expression lines) during the result-decorations pass

For the "valid expression lines" tracking — the `provideDecoration` method already returns `undefined` for unparseable lines. We can track:
- A `Set<number>` of successfully solved lines during the result pass
- Pass this set to the highlight builder

The decorations merging strategy:
- Build result decorations (widgets) into one builder
- Build highlight decorations (marks) into a separate builder
- Both return `DecorationSet`
- The `decorations` getter returns the combined set — but in CodeMirror, each `PluginValue` only exposes one `DecorationSet`
- Solution: Build both into the SAME `RangeSetBuilder`, so result widgets and highlight marks coexist in one `DecorationSet`. This is clean because `RangeSetBuilder` accepts overlapping ranges — widgets are zero-width (point decorations at line end), marks are ranged decorations covering tokens.

Actually, looking at `RangeSetBuilder` — it supports adding individual decorations one at a time. We just need to add ALL decorations (both widgets and highlights) to the same builder. The `builder.finish()` call produces a `DecorationSet` containing both.

Modified flow in `buildDecorations()`:
```
for each visible line:
  if expression parsed successfully:
    add result widget decoration (existing logic)
    add highlight mark decorations for each token (new logic)
```

This is simpler than having two separate providers.
