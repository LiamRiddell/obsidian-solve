# Project Review and Gap Analysis

## 1. Project Overview
**Obsidian Solve** is a plugin for the Obsidian note-taking application that provides real-time calculation capabilities. It allows users to perform arithmetic, date manipulations, percentage calculations, unit conversions, and more directly within their notes.

**Core Technologies:**
- Obsidian Plugin API (TypeScript)
- CodeMirror 6 for editor integration
- Custom parsing engine: Lexer (`moo`) -> Parser (Pratt) -> VM (Stack-based)

**Architecture Flow:**
1.  **Lexer (`src/engine/lexer/Lexer.ts`)**: Tokenizes input text using `moo` with markdown-aware states.
2.  **Parser (`src/engine/parser/Parser.ts`)**: Pratt parser generating bytecode via `BytecodeBuilder`.
3.  **VM (`src/engine/vm/VM.ts`)**: Executes bytecode, manages stack, variables, and invokes builtins/providers.
4.  **Engine (`src/engine/engine/ExpressionEngine.ts`)**: Orchestrates parsing, execution, caching (`MemoCache`, `LineCache`), and dependency tracking (`DependencyGraph`).
5.  **Integration (`src/codemirror/MarkdownEditorViewPlugin.ts`)**: CodeMirror plugin that triggers evaluation and renders results/widgets.

## 2. Architecture & Code Quality Review

### Strengths
- **Modular Design**: Clear separation of Lexer, Parser, VM.
- **Extensibility**: `Parselet` system allows adding new syntax.
- **Performance Features**: `MemoCache`, `LineCache`, and `DependencyGraph` for incremental updates.
- **State Management**: `ScopeManager` handles variable scoping.

### Code Quality Issues Found
1.  **Type Safety Violations** (`src/main.ts:132`):
    -   `const { containerEl } = editor as any;` - Using `any` bypasses type checking. Should define an interface for the editor container.
2.  **Inefficient String Handling** (`src/engine/vm/VM.ts:241`):
    -   `args.unshift(vm.pop())` - `unshift` is O(n). For large argument counts, this is slow. Use `push` and reverse or iterate backwards.
3.  **Duplicate Event Emission** (`src/main.ts:42-46`):
    -   `SolveEngineReady` is emitted twice in `onload`. Likely a copy-paste error.
4.  **Magic Numbers in OpCode** (`src/engine/parser/OpCode.ts`):
    -   OpCode values are hardcoded integers. While functional, it makes refactoring risky. Consider using a sequential enum or auto-incrementing constants.
5.  **Complex VM Dispatch** (`src/engine/vm/VM.ts:107`):
    -   Large switch statement. While V8 optimizes this, it limits flexibility for plugin-defined opcodes (currently limited to `PLUGIN_CUSTOM` range).
6.  **Lexing Performance** (`src/engine/lexer/MarkdownLexer.ts`):
    -   Uses `moo` states effectively, but processing large documents line-by-line without efficient skipping of non-expression lines could be a bottleneck.

### Architecture Gaps
1.  **Community API** (`TODO 5`):
    -   Current `SolveAPI` allows registering handlers, but the system seems designed for single-instance registration. The TODO suggests plugins should be able to register *many* parslets/providers in one package.
2.  **Human Readable Output** (`TODO 6`):
    -   The `FormatEngine` exists and handles formatting (e.g., dates, percentages). The gap is ensuring full parity with the previous Ohm-based implementation's output formats.
3.  **Vector Syntax** (`TODO 7`):
    -   Verified: `VectorParselet` uses `(x,y,z)` syntax (parentheses), which matches the requirement. Tests confirm this.
4.  **Internationalization** (`TODO 1`):
    -   `FormatEngine` uses locale settings for decimal separators, but the Lexer/Parser might not fully support locale-specific number parsing (e.g., comma as decimal separator).

## 4. Execution Plan

1.  **Fix Type Safety**:
    -   Refactor `src/main.ts` to remove `any` casts. Define interfaces for Obsidian editor internals if necessary.
2.  **Fix Duplicate Event**:
    -   Remove duplicate `pluginEventBus.emit(EPluginEvent.SolveEngineReady, solveAPI)` in `src/main.ts`.
3.  **Optimize VM Stack Operations**:
    -   Refactor `CALL_BUILTIN` in `src/engine/vm/VM.ts` to use `push` + reverse iteration instead of `unshift`.
4.  **Clean Up OpCode Definitions**:
