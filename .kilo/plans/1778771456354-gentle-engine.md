# Plan: Refactor CurrencyExchange.ts with Optimized Enterprise Architecture

## 1. Problem Analysis
The current `CurrencyExchange.ts` implementation has several issues:
-   **Static Fallbacks**: Hardcoded rates are outdated and useless when the API is down.
-   **API Usage**: While it uses an API (`open.er-api.com`), the fallback mechanism is flawed.
-   **Missing Documentation**: Lack of TSDoc comments.
-   **Test Coupling**: Tests rely on hardcoded fallback rates, making them brittle.
-   **Architectural Limitations**: No separation of concerns, not optimized for performance, no background processing, not reusable.

## 2. Proposed Solution
### 2.1. Enterprise Architecture Design
-   **Separation of Concerns**: Extract polling logic into a reusable `PollingEngine` class.
-   **Background Processing**: Use Web Workers for polling to avoid blocking the main thread.
-   **Extensibility**: Design for future WebSocket/SSE support via plugin architecture.
-   **Performance**: Optimize data structures, minimize API calls, implement caching strategies.
-   **Reusability**: PollingEngine should be generic and usable by other components.

**Architecture Decision Record (ADR):**
-   **Decision**: Use Web Worker for currency polling despite infrequent intervals.
-   **Justification**: User request for enterprise architecture; prepares for future high-frequency data sources; isolates network I/O from main thread.
-   **Trade-off**: Added complexity; worker communication overhead. Mitigated by batching and debouncing.

### 2.2. New Architecture Components
1.  **`PollingEngine` Class** (`src/engine/core/PollingEngine.ts`):
    -   Generic polling mechanism with configurable intervals.
    -   Supports multiple data source types via strategy pattern (HTTP, WebSocket, SSE).
    -   Thread-safe rate limiting and error handling with circuit breaker pattern.
    -   Event-driven design with observable pattern for data updates.
    -   Configurable retry logic with exponential backoff.

2.  **`CurrencyPollingWorker`** (`src/workers/currency-polling.worker.ts`):
    -   Dedicated Web Worker for background currency rate polling.
    -   Uses `PollingEngine` internally for HTTP polling.
    -   Communicates with main thread via `postMessage` API.
    -   Self-contained with error handling and fallback logic.
    -   Follows existing worker pattern in `playground/src/engine.worker.ts`.

3.  **`CurrencyExchange` Class** (`src/engine/uom/CurrencyExchange.ts`):
    -   Public API facade that communicates with the worker.
    -   Maintains in-memory cache of rates for fast access.
    -   Implements fallback strategy (last successful response).
    -   Provides TSDoc-documented API for consumers.
    -   Preserves singleton pattern (`sharedCurrencyExchange`).

4.  **`RateCache` Interface** (`src/engine/core/RateCache.ts`):
    -   Abstract cache layer for rate storage.
    -   Supports in-memory and persistent storage strategies.
    -   TTL (Time-To-Live) support for cache invalidation.

### 2.3. API Selection
-   **Primary**: `api.frankfurter.dev` (free, no key, well-documented, no rate limits).
    -   Endpoint: `https://api.frankfurter.dev/v2/rates?base=USD`
    -   Returns array of `{ date, base, quote, rate }` objects.
-   **Fallback Strategy**:
    -   Initial: Static fallback rates (for offline/first load).
    -   Runtime: Last successful API response cached in memory.
    -   Persistent: Optional localStorage cache for offline usage.

### 2.4. Implementation Details
-   **TSDoc**: Comprehensive JSDoc/TSDoc for all public APIs and complex logic.
-   **Error Handling**: Graceful degradation, retry logic with exponential backoff, circuit breaker.
-   **Performance**: 
    -   Async/await for non-blocking operations.
    -   Debounced updates to prevent excessive worker communication.
    -   Efficient data structures (Maps for O(1) lookups).
-   **Testing**: 
    -   Unit tests for PollingEngine with mocked sources.
    -   Integration tests for worker communication.
    -   Mock Web Workers in Jest environment using `jest-environment-node`.

## 3. Implementation Steps
### 3.1. Create PollingEngine (`src/engine/core/PollingEngine.ts`)
```typescript
interface PollingConfig {
  interval: number;
  maxRetries: number;
  retryDelay: number;
  backoffMultiplier: number;
}

interface DataSource<T> {
  fetch(): Promise<T>;
  getType(): 'http' | 'websocket' | 'sse';
}

class PollingEngine<T> {
  private config: PollingConfig;
  private dataSource: DataSource<T>;
  private intervalId: ReturnType<typeof setInterval> | null = null;
  private retryCount = 0;
  private isRunning = false;
  
  constructor(dataSource: DataSource<T>, config: Partial<PollingConfig>);
  start(): void;
  stop(): void;
  onUpdate(callback: (data: T) => void): void;
  private poll(): Promise<void>;
  private handleError(error: Error): void;
}
```

### 3.2. Create HTTP Data Source (`src/engine/sources/HttpDataSource.ts`)
```typescript
class HttpDataSource<T> implements DataSource<T> {
  private url: string;
  private parser: (response: any) => T;
  
  constructor(url: string, parser: (response: any) => T);
  fetch(): Promise<T>;
  getType(): 'http';
}
```

### 3.3. Create Web Worker (`src/workers/currency-polling.worker.ts`)
-   Import `PollingEngine` and `HttpDataSource`.
-   Set up polling for Frankfurter API.
-   Post messages to main thread on data update.
-   Handle errors and retry logic.
-   Follow pattern from `playground/src/engine.worker.ts`.

### 3.4. Refactor CurrencyExchange (`src/engine/uom/CurrencyExchange.ts`)
-   Remove direct API calls.
-   Communicate with worker via `postMessage`/`onmessage`.
-   Maintain local cache of rates.
-   Add TSDoc comments.
-   Implement fallback logic using cached data.
-   Preserve `sharedCurrencyExchange` singleton.

### 3.5. Update Tests
-   Mock Web Worker in Jest setup (using `jest-environment-node`).
-   Update `CurrencyExchange.spec.ts` to test worker communication.
-   Add tests for PollingEngine with mocked data sources.
-   Add test setup file if needed (`test/setup.ts`).

### 3.6. Integration

-   Ensure proper cleanup on plugin deactivation.

## 5. Risks & Mitigations
-   **Web Worker Compatibility**: 
    -   Risk: Worker API may differ in Obsidian's Electron environment.
    -   Mitigation: Test in both desktop and mobile environments; use standard Web Worker API.
-   **API Rate Limits**: 
    -   Risk: Frankfurter API may rate-limit excessive requests.
    -   Mitigation: Use 30-minute polling interval; implement request deduplication.
-   **API Downtime**: 
    -   Risk: Service unavailable or network issues.
    -   Mitigation: Fallback to cached rates; implement exponential backoff retry.
-   **Performance Overhead**: 
    -   Risk: Worker communication overhead may outweigh benefits for infrequent polling.
    -   Mitigation: Batch updates; debounce rapid requests; measure performance impact.
-   **Memory Leaks**: 
    -   Risk: Unreleased listeners or intervals.
    -   Mitigation: Proper cleanup in `stop()` methods; use weak references where appropriate.
-   **Test Complexity**: 
    -   Risk: Mocking Web Workers in Jest may be complex.
    -   Mitigation: Use `worker-loader` or manual mocking; isolate worker logic for unit testing.
