Segment Tree (Treap) — How It Solved Our Document Ordering Problem

The ELI5 version first, then the developer deep-dive.

ELI5: Imagine a Library

You're a librarian. You have 10,000 books on one long shelf. Each book has a permanent ID sticker — that's its lineId. Books are ordered left-to-right by their position on the shelf.

The Flat Array (Old Way)

You keep a numbered list on a clipboard:

8 books (C through J) had to be physically shifted right. And on your clipboard, you had to erase and rewrite 8 entries.

Now imagine doing this every time you type a single character in a 100,000-line code file. O(N) — SLOW

The Segment Tree (New Way)

Instead of a flat shelf, imagine the books are in nested boxes. Each box has a label saying how many books are inside it:

To insert a new book at position 3 (between B and C):

  1. Walk down from the top box: "I need position 3. Box has 10 books. Left box has 4 books. 3 ≤ 4, so go left."
  2. At the left box: "I need position 3. Inner-left has 2 books (A,B). 3 > 2, so go right. Now I need position 3-2-1 = 0."
  3. Insert the new book, update the counts going back up: left box now says 5, root now says 11.

Only 3 boxes were touched. The right half of the tree was never even visited. O(log N) — FAST

That's the core idea. Each box remembers its size, so we can jump to any position by counting left children, without ever looking at the whole shelf.

Developer Deep-Dive: Implementation Details

The Problem We Actually Had

Our DocumentModel tracks document lines as LineState objects keyed by an immutable lineId. The old implementation used a flat array lineOrder: number[] to map positions → IDs:

// OLD: flat array — O(1) position lookup, O(N) structural edits
class DocumentModel {
  private lineOrder: number[] = [];  // [id1, id2, id3, ...]
  private lines: Map<number, LineState>;

  getLineAt(position: number): LineState | undefined {
    const lineId = this.lineOrder[position - 1]; // O(1) — nice!
    return this.lines.get(lineId);
  }

  applyChanges(changes) {
    // O(N) — painful: Array.splice shifts every element after the change
    this.lineOrder.splice(startIdx, deleteCount, ...newIds);
    // Position cache invalidated for ALL lines → rebuild on next getLinePosition()
  }
}

The problem: Array.splice() is O(N). When you type one character that inserts a line at position 5,000 in a 10,000-line document, JavaScript shifts 5,000 array elements in memory. And we do this on every keystroke during rapid typing.

The Solution: Order-Statistic Treap

A Treap = Tree + Heap. It's a binary search tree ordered by position, with random priorities to keep it balanced. Each node stores:

interface Node {
  lineId: number;       // The actual line ID (payload)
  size: number;         // Total nodes in this subtree (incl. self)
  priority: number;      // Random priority → keeps the tree balanced
  left: Node | null;    // All positions BEFORE this node
  right: Node | null;   // All positions AFTER this node
}

The size field is the key: it tells us how many nodes are in each subtree. This lets us find the k-th element in O(log N) — just like counting books in boxes.

Core Operations Walkthrough

1. getAt(3) — Find the 4th element (0-based)

Walk from root, comparing the target index against the left subtree size at each step:

3 steps for a tree of 8 elements. For 100K elements: ~17 steps. O(log N)

2. spliceAt(2, 2, [27, 28]) — Replace elements at index 2–3

The most important operation. It's how applyChanges() handles CodeMirror edits. We use split & merge:

1
Split the tree at index 2
split(root, 2) → [left, midRight]
left = first 2 elements (indices 0-1), midRight = remaining (indices 2+)
2
Split midRight at index 2 (the delete count)
split(midRight, 2) → [mid, right]
mid = elements to remove (indices 2-3), right = everything after
3
Build a new balanced treap from the inserted IDs
buildTreap([27, 28], 0, 2) — O(insertCount) divide-and-conquer
4
Merge the three pieces back together
root = merge(merge(left, newTree), right)
Merge uses priority-based comparison to maintain the treap's heap property

Total: O(log N + deleteCount + insertCount). For a single-line edit on a 100K doc: ~17+1+1 = 19 operations. The flat array needed ~100,000. ~5,000× faster

3. getRange(0, 29) — Render a 30-line Viewport

This is called on every animation frame during scrolling. The old per-line getAt(i) loop was O(viewport × log N). Now we do a single in-order walk that skips entire subtrees outside the range:

private collectRange(node, targetStart, targetEnd, offset, result) {
  // Skip ENTIRE left subtree if it can't overlap the range
  if (nodeIndex > targetStart && node.left)
    this.collectRange(node.left, targetStart, targetEnd, offset, result);

  // Include this node if in range
  if (nodeIndex >= targetStart && nodeIndex <= targetEnd)
    result.push(node.lineId);

  // Skip ENTIRE right subtree if it can't overlap the range
  if (nodeIndex < targetEnd && node.right)
    this.collectRange(node.right, targetStart, targetEnd, nodeIndex + 1, result);
}

Result: O(viewport + log N). The log N part finds the start, then we walk ~30 nodes. ~1/3 the work of the old per-line loop

The trade-off: We pay a small cost on reads (the hot render path) and memory, and gain massive wins on writes (every keystroke). Since typing is the bottleneck users actually feel, this is the right trade.

Why a Treap and Not a Plain BST?

A plain binary search tree can become degenerate — if you insert lines in sorted order (which is exactly what setDocument() does), a naive BST becomes a linked list, and all operations degrade to O(N).

The Treap adds a random priority to each node and maintains a heap invariant: every node's priority is greater than its children's. This randomizes the tree structure regardless of insertion order, guaranteeing O(log N) depth with high probability.

// split() walks the tree, comparing indices against left subtree sizes.
// It returns [leftSubtree, rightSubtree] without breaking the treap invariants.
function split(node: Node | null, index: number): [Node | null, Node | null] {
  if (!node) return [null, null];
  const leftSize = node.left ? node.left.size : 0;

  if (index <= leftSize) {
    // Split point is in the left subtree
    const [left, right] = split(node.left, index);
    node.left = right;
    updateSize(node);
    return [left, node];
  } else {
    // Split point is in the right subtree
    const [left, right] = split(node.right, index - leftSize - 1);
    node.right = left;
    updateSize(node);
    return [node, right];
  }
}

// merge() recombines two treaps using priority-based rotation.
// All keys in `left` are positionally before all keys in `right`.
function merge(left: Node | null, right: Node | null): Node | null {
  if (!left) return right;
  if (!right) return left;

  if (left.priority > right.priority) {
    left.right = merge(left.right, right);
    updateSize(left);
    return left;
  } else {
    right.left = merge(left, right.left);
    updateSize(right);
    return right;
  }
}

For bulk initialization (setDocument), we use buildTreap() which does divide-and-conquer to build a perfectly balanced tree in O(N) time — faster than inserting N elements individually (which would be O(N log N)).

How It All Fits Together

/* ── DocumentModel ──────────────────────────────────── */
// Public API unchanged. All methods delegate to SegmentTree internally.

export class DocumentModel {
  private lines: Map<number, LineState>;        // lineId → full state (O(1) by ID)
  private orderTree: SegmentTree;              // position → lineId (O(log N))
  private _positionCache: Map<number, number> | null; // lineId → position (lazy O(N) build)

  getLineAt(pos: number) {
    const id = this.orderTree.getAt(pos - 1);  // SegmentTree.find
    return id !== undefined ? this.lines.get(id) : undefined;
  }

  getVisibleLines(start, end) {
    const ids = this.orderTree.getRange(start - 1, end - 1); // Single tree walk
    return ids.map(id => this.lines.get(id)!).filter(Boolean);
  }

  applyChanges(changes) {
    for (const c of changes) {
      const removed = this.orderTree.spliceAt(c.start - 1, c.deleteCount, newIds);
      for (const id of removed) {
        result.removed.push(id);
        this.lines.delete(id); // Clean up LineState for removed lines
      }
    }
    this._positionCache = null; // Invalidate lazy cache
  }
}

The _positionCache is a lazy optimization: getLinePosition(lineId) is O(N) the first time (iterates the tree to build a Map), then O(1) on subsequent calls. The cache is invalidated (= null) after every structural edit — cheap and effective.
