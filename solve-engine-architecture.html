Key design principle: SegmentTree is private to DocumentModel. ThreeTierEvaluator has zero knowledge of whether line order is stored in an array or a tree. It only calls doc.getLineAt(pos) — never doc.orderTree.

2. Layer 1 — SegmentTree (Order-Statistic Treap)

What problem does it solve?

Documents have lines. When you type, lines get inserted or deleted. In a flat array, inserting one line at position 500 forces all 9,500 lines below it to shift — O(N). A Segment Tree keeps lines in a balanced tree structure, so insert/delete at any position is O(log N) — about 17 steps for 100,000 lines.

Treap Node Structure

// Each node stores:
interface TreapNode {
  lineId: number;        // The line's persistent ID
  priority: number;      // Random heap weight (balances the tree)
  size: number;         // How many nodes in this subtree
  left: TreapNode | null;
  right: TreapNode | null;
}

3. Layer 2 — DocumentModel

What problem does it solve?

The SegmentTree stores which line comes first (order), but it doesn't store what's in each line. DocumentModel wraps the tree with a per-line state store, giving every line a persistent immutable ID that survives all edits.

DocumentModel Internals

export class DocumentModel {
  // ── The heart of it ──
  private lines: Map<number, LineState>;      // lineId → state (O(1) lookup)
  private orderTree: SegmentTree;           // lineId order (O(log N) splices)
  private _positionCache: Map<number,number>; // lineId → 1-based position (lazy)

  // ── Public API (design contract) ──
  getLineAt(position: number): LineState        // tree.getAt(pos-1) → lines.get(id)
  applyChanges(changes: LineChange[]): ApplyChangesResult  // tree.spliceAt(...)
  getVisibleLines(start, end): LineState[]  // tree.getRange(...) → lines.get(id)
  updateLineResult(id, result, bytecode, ...): void
  markDirty(lineId: number): void
}

4. Layer 3 — ThreeTierEvaluator

What problem does it solve?

Not every line needs the same treatment. A freshly typed line needs full lex→parse→compile→execute. A clean line scrolled into view just needs its cached bytecode executed. An invisible line only needs to be compiled for dependency tracking. Three tiers, three strategies, one evaluator.

Two Evaluation Entry Points

// 1. Document changed (edit) — full re-evaluation from line 1
evaluate(viewport: ViewportRange): EvalResult {
  for (pos = 1; pos <= viewport.endLine; pos++) {
    const state = this.doc.getLineAt(pos);  // ← DocumentModel public API
    const tier = state.dirty ? (inViewport ? Tier1 : Tier3) : (hasBytecode ? Tier2 : Skip);
    this.evaluateSingleLine(state, pos, inViewport);
  }
  this.pageManager.maintainAfterEval(viewport, this.doc);
}

// 2. Scroll only — skip to viewport, restore VM checkpoint, execute cached
setViewport(viewport: ViewportRange): EvalResult {
  // Guard: if dirty lines exist before viewport, fall back to evaluate()
  if (this.hasDirtyLinesBefore(viewport.startLine)) return this.evaluate(viewport);

  this.pageManager.maintainAfterEval(viewport, this.doc); // evict cold pages
  this.preloadNextPages(viewport);                  // preload 2 pages in scroll direction
  this.restoreTo(viewport.startLine - 1);              // O(1) VM restore from nearest checkpoint
  return this.collectEvalResults(viewport.startLine, viewport.endLine); // Tier 2 only
}
Key insight: setViewport() skips all lines before the viewport entirely. It restores the VM from the nearest checkpoint (prototypal chain, O(1)), then executes only the visible lines from cached bytecode. A 30-line viewport evaluates in <1ms regardless of document size — O(visible) instead of O(document).

Design contract: ThreeTierEvaluator calls doc.getLineAt(pos) (public API) — it never accesses doc.orderTree or doc.lines. DocumentModel could swap SegmentTree for a B-Tree, a rope, or a flat array tomorrow, and ThreeTierEvaluator wouldn't need a single line changed. This is the definition of clean architecture.
